    Three concrete options — pick one, they trade off speed vs. rigor differently.

    ## 1. Vertical Slice + TDD (what I proposed for Month 1)
    Build one thin path end-to-end (Login OTP: 1 endpoint, 1 test, 1 review) before starting the next. Every slice: RED → GREEN → REFACTOR, gates (ruff/mypy/bandit) must pass before you look at it.
    - **Best when:** quality is the bottleneck (your stated problem), team is small (you + me), you can review each slice.
    - **Cost:** slower total throughput early on — Month 1 covers maybe 1-2 screens, not 6.
    - **Payoff:** defect rate becomes measurable and trends down, because nothing ships unverified.

    ## 2. Contract-First (schema-driven)
    Before any code: freeze the OpenAPI/Pydantic contracts and Kafka event schemas for the *entire* funnel (we already drafted this). Then implement against frozen contracts in parallel — API layer, DB layer, frontend — each side only trusts the contract, not each other's internals.
    - **Best when:** you have (or will have) more than one person/agent working simultaneously, and want to avoid integration drift.
    - **Cost:** upfront contract work has to be right, or every downstream slice inherits the same wrong assumption — this is exactly where my earlier unlabeled inference was risky.
    - **Payoff:** parallel-safe; screens/services can be built out of order without blocking each other.

    ## 3. Strangler / Reference-Anchored Build
    Instead of designing from a mockup + inference, pick one real product (IndiGo, since we already verified live) as the literal reference implementation for field shapes, flows, and edge cases. Every screen gets built by matching IndiGo's actual behavior first, then diverging only where "International Smile" intentionally differs (premium positioning, different fare names).

    - **Cost:** requires repeated live verification passes (like the goindigo.in check) before each slice — more browsing time per feature.
    - **Payoff:** almost eliminates the "inferred vs. observed" ambiguity that caused the earlier doc problem — everything traces to a real, currently-live product.
